# AMD 曲线目标列表与设置入口

这是查询实现 `06b477c` 之后的静态研究，不计入该提交的运行时功能或云端测试数字。
[固定 ELF 证据](validation/legacy-amd-curve-targets-static.json)包含五个完整函数、
原 UI 构造中的 473 字节目标列表片段、比较常量及四段 PM 对象字段赋值。未执行曲线设置或真实硬件访问。

## 原版目标列表的来源

`cpufunctions` 的曲线槽读取对象 `+1d8` 处的二维整数向量，每行前两个整数作为 CCD/core。
其构造片段 `76301f..7631f8` 从对象 `+b18` 的 PM 数据向量生成这些行：

| 项目 | 原指令行为 |
|---|---|
| 遍历长度 | 取第一列长度；空外层向量走范围异常 |
| 筛选列 | 对象 `+f8c` 指定的列；访问前检查列和行边界 |
| 长度不超过 16 | 仅接受该列浮点值大于双精度常量 `0.001` 的行 |
| 长度超过 16 | 不论该浮点比较结果如何，全部纳入 |
| 输出编号 | 原表行号 `i` 对应 `CCD=i/8`、`core=i%8` |

这个过程没有读取逐核心熔丝，不能据此宣布已恢复物理核心映射。
目前仍缺 PM 表版本、列布局、有效核心标志和固件编号之间的完整契约。
新查询界面因此不自动填充这些编号，也不把查询成功当作物理核心存在的证明。

## “fused CCD” 名称与实际行为

`get_fused_ccd` 在 Shimada、GPT、Granite 标志或部分 PCI 身份命中时，
转而使用 `get_amd_native_thread_count`；此路径不读取旧分支中的 `5d228/5d218` 寄存器。
线程函数调用 CPUID leaf 1，并截取返回 EBX 的 `23:16`，忽略包装函数是否成功。
这个八位原值经阈值表变为 `1,2,4,8,10,12,14,16`；零值也落入返回 1 的分支。
这只能证明原算法，不能把函数名理解为已经验证过的 CCD 熔丝结果。

## 查询与设置不能按名称互换

曲线 Apply 槽的组合框第 0 项调用 `AMD_PM_LOG::set_curve_opt`，其它项取上述目标行后
调用 `AMD_PM_LOG::set_curve_opt_percore`。之后独立调用 `AMD_PBO::get_co` 收集显示值。
槽的调用证据见[前次完整静态记录](validation/legacy-amd-curve-query-static.json)。

另一个同名函数 `AMD_PBO::set_curve_opt` 使用 F8/FC 和对象保存的设备字段，
而本轮恢复的 `get_co` 使用 B8/BC 并硬编码 BDF0。
两个同名 setter 都包含多次连续提交，并在读响应之前释放原互斥锁；它们不能直接改名复用查询通道。
还需逐项确认设置命令、参数含义、完成状态和附带作用，才能实现带回读校验的曲线写入。

`AMD_PM_LOG::set_curve_opt_percore` 将输入整数先与 `0x0f0fffff` 相与，
再合并 `CCD << 28` 和 `(core & 15) << 20`。掩码还保留输入的 27:24 位，
不能简单解释为已确认的低 16 位 CO 数值。
对象的命令来自 `+7c` 与 `+84`，通信端口来自 `+28/+2c`；
构造虽然先填 F8/FC，后续还会根据候选端口数组覆写，部分路径调用 `Wr_Scratch2(1)`。
这些初始化和附带状态尚未形成可用设置协议，因此新实现只开放独立查询。
