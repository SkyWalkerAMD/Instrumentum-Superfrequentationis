## 本次修正

### R1：MMIO 跨页访问映射不足（高优先级）

基线模块的 `mmio_read/write()` 和 HAL `direct_mem()` 只映射起始页。例如页末最后一字节处的
8 字节访问会超出映射。GUI 表单的自然对齐检查减少了当前 UI 的触发面，但设备和 HAL 输入不受
该表单保护。此处为源码发现，没有在硬件上发送越界物理地址进行复现。

模块改用 `ioremap(phys, width)`，HAL 映射 `offset + width`，同时检查 64 位地址范围溢出；仍是
一次对应宽度的访问，不拆成多次硬件读写。[x86 ioremap 实现](https://raw.githubusercontent.com/torvalds/linux/v4.18/arch/x86/mm/ioremap.c)
会按请求范围覆盖页面并返回包含原始偏移的指针。HAL 无硬件 syscall 替身覆盖页末 2/4/8 字节读写。
这只修正映射覆盖，不承诺某块设备支持未对齐访问，也不证明所有物理地址有效。

### R2：PCI 参数可以越过四字节缓冲或被截断（高优先级）

基线 `direct_pci_read()` 把任意 `int width` 作为 `pread` 长度，目标只有一个 `uint32_t`；写路径
同样可能越读局部值。模块则对非法宽度默认 dword，对 offset 使用 `& 0xfc`，可能访问另一个寄存器。

HAL 和模块在访问前校验宽度 1/2/4、BDF、自然对齐及首 256 字节；保持既有 domain 0 范围。
模块在 u64 原字段上验证再转换，避免高位截断。回归要求非法参数在 module/direct 两种 HAL
后端都返回 EINVAL、不发任何访问、不修改输出值。当前 GUI 已有这些限制，此次补足底层入口。
**PCI 与系统驱动之间的同步问题没有因此解决，见 R7。**

### R3：模块握手和完成字过于宽松（中优先级）

基线读令牌失败/不足 8 字节仍以 token=0 接受模块；现在释放 mmap/fd，按原有后端规划回退或
报告不可用。回归覆盖 -1 和 0..7 字节的令牌读，检查资源释放。

基线把 done=2、正高位状态或其他非法非零值当作成功。HAL 现在只接受完整值 1，或低 32 位为 1、
高位为 Linux 负 errno（-4095..-1）；其他值返回 EPROTO，错误不覆盖调用者读数。采用 acquire
读取完成字，但没有声称这能修复旧模块先发布 done 的顺序问题。96 字节字段、MMIO token 和 CPU
请求的目标 CPU 保持原样。原 GUI 仍不会使用这段 HAL，不能据此宣称原调用者已修复。

### R4：对拍可能出现无效通过（高优先级，测试可信度）

基线允许 `--old`/`--new` 指向同一设备；live 模式现在在打开前比较字符设备号，拒绝同路径和
符号链接别名。操作者仍须确认两节点实际模块归属，并在整轮测试中保持节点不变；这不是防止
恶意节点替换的安全边界。脚本也在采集前拒绝明显自比较。

原判定将第二次 old 读取失败归入 volatile；只要另有 stable match，unreadable/volatile-oob
也可被退出码 0 掩盖。现在这些未解决项返回 2，硬分歧优先返回 1；volatile 区间内仍只算未证明项。
自测增加“成功地址不能掩盖读取失败”和第二次 old 失败用例，Linux 输入回归用 `/dev/null` 及其
别名验证拒绝发生在设备打开/请求之前。没有真实硬件 I/O。

采集器 completed 收紧为完整 done==1，保存原 write errno；trace 读取另核验 wrote=96/done=1，
避免把历史宽松 completed 标志独立当作成功。原格式不变。

### R5：重复加载探针的通过条件不完整（中优先级）

基线记录 `/dev/mydev`，但没有将其存在作为硬门禁；卸载失败被 cleanup 隐藏。本次要求 class
和字符节点同时可见，显式卸载成功并确认模块消失，将结果写入 JSON；原 fallback trap 仅用于
异常退出清理。已有节点时拒绝启动探针。仍只在授权研究分支的临时 runner 使用，不访问寄存器。

### R6：文档和源码注释过度外推（中优先级）

校正“bug-for-bug 兼容所以旧 GUI 能直接用”“签名模块 always works”“capture 不影响时序”及
“volatile 不会漏掉差异”等表述。历史日志和已有观测 JSON 保留原时间点的事实；指南正文说明当前
限制。HAL 头文件本次仅修正文档约定，函数接口不变；本地固定哈希同步记录本次已说明的修正，
canonical ABI 头的原始固定哈希不变。

## 未解决问题与继续研究顺序

### R7：PCI/EC 系统驱动协调（高优先级，源码证据，未真机复现）

模块自有 `pci_lock` 只能串行化自身的 CF8/CFC 访问，不能与系统 PCI 配置访问共享锁。
[Linux PCI access.c](https://raw.githubusercontent.com/torvalds/linux/v4.18/drivers/pci/access.c)
提供由核心锁保护的配置访问及 `pci_user_*` 路径。下一步应评估核心 API 的设备生命周期/错误语义，
以真实目标 Kbuild 和离线替身验证，再移除独立 CF8/CFC 序列；不能只扩大本模块的锁范围。

EC 自有 raw spinlock 包住最多三次 100000×udelay(1) 的等待，且未和 ACPI EC 驱动共享事务锁；
单次请求可能长时间关闭本地中断。对照[Linux ACPI EC 事务实现](https://raw.githubusercontent.com/torvalds/linux/v6.12/drivers/acpi/ec.c)，
系统驱动使用自身 mutex、平台 global lock 及发现的设备。当前 GUI 没有 EC 页面/自动 EC 操作。
不能假设固定 0x62/0x66 对四块主板都正确；恢复 EC 前须核对平台定义和内核接口，不进行猜测读写。

### R8：原 GUI 接入和错误契约（高优先级，已有模拟/静态证据）

原版忽略 write 返回且等待完整 64 位 done=1；当前模块高位 errno 会令原版等待不结束。
guard 是可选的错误退出实验，不是恢复错误后 GUI 工作的方案，也不能打断阻塞在内核内的 write。
旧模块部分样本先 done 后 result，global request 的并发也没有解决。

真实 EEXIST 只证明同名有效模块再次加载的内核返回。接续静态研究已核实候选顺序/目录拼接
（见下节），它在四块目标主板上是否实际到达该分支仍需跟踪。不能以匿名返回值注入、CPU/主板
伪装或放宽主窗口门禁替代验证。见[接入报告](legacy-module-handoff.md)与[邮箱契约](legacy-mailbox-contract.md)。

### R9：HAL / capture 的剩余边界（中优先级）

- HAL 没有模块能力握手；能 read/mmap 不足以证明任意节点支持扩展操作码。旧模块仅在 MMIO
  对拍使用；不要让重构 GUI 向未经确认的旧节点发送新扩展命令。
- direct iopl 缓存属于 handle，而权限属于 OS thread；当前头文件明确端口句柄不得跨线程迁移。
  后续应改成每调用线程建立权限。当前基础 GUI 不提供端口/EC 页面。
- direct CPUID/TSC 本身在当前 CPU 执行；GUI 的 CPUID 路径已经固定所选 CPU 并恢复 affinity，
  已有真实本地 CPUID 回归，不能误报成 GUI 的目标 CPU bug。
- capture 不完整处理 dup/munmap/mremap/fd 并发和任意路径别名；只有完整 96 字节写才记录。
  已知映射双别名为同页不代表全部生命周期安全。先补合成生命周期测试再扩用采集器。
