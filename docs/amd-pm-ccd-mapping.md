# Shimada PM 固件 CCD 槽位映射

GUI 与 CLI 共用可选的 CCD 映射读取：

```sh
octool-cli amd-pm-native-read --cpu 0 --map-ccd
```

GUI 在 AMD PM 页面勾选 `Map firmware CCD slots` 后读取 native PM 表。
逐核和 CCD 存储视图会显示 `FW CCD`，逐核视图另列 `core slot`。
`--cpu` 仍是用于校验硬件身份的逻辑 CPU；`FW CCD` 是固件 MP5 目标号。
二者不能互换。读取仅覆盖 Shimada family 1Ah/model 08h、PCI 1022:153a、
domain 0 / 00:00.0 和精确 SMU `00732E00h`（115.46.0）。
原有不带 `--map-ccd` 的 PM 读取行为保持兼容。

## 已闭合的映射链

固定输入来自 ASUS Pro WS TRX50-SAGE WIFI 1317。
SMU SHA256 `a2f3724ccaef1d67db04afb553816f111dc86207480b28d7998cc15fa92ea7d7`；
MP5 SHA256 `b5e9c94ef3a27d55a95c1a0d703cc7041b734f9475d44b8eecd49a15794cdeaf`。

| 环节 | 字节核对后的证据 |
|---|---|
| 存在判断 | RSMU `A5h → 2F828h` 从 `7444h` 取 16 位存在掩码，按参数低四位取位；存在回复 `01h`，不存在回复 `FEh` |
| 初始化请求 | MP5 `FDCh` 将 `19B80h` 的 `70h` 字节区域作为参数，调用 `36C88h(3, pointer)` |
| SMU 接收 | `21910h` 将各目标的指针保存到 `7444h + 8 + 4*target`，收齐后调用 `215A8h` |
| 配置包 | `215A8h` 遍历目标 0..15；包 `+00h` 是目标号，`+02h` 是活动序号，`+0Dh` 是表宽度，`+14h` 是存在序号 |
| PM 输出 | MP5 `37D40h` 从 `19B80h+0Dh/+14h` 读取宽度和存在序号；后续整数拷贝按这个序号写入表 |

因此 PM 的 CCD 槽位按**存在掩码置位的升序**排列。例如掩码 `8001h`
对应槽位 0 → 固件 CCD 0、槽位 1 → 固件 CCD 15；不能按连续 CCD 0/1 显示。
逐核数组的槽位分组为 `ccd_slot = slot / 8`、`core_slot = slot % 8`。
这里没有恢复禁用核心掩码、Linux CPU/APIC 对应关系、socket 间的物理 CCD 对应关系。
存在序号与活动序号是两个字段，不能混用。

[指令回放脚本](../analysis/tools/firmware-pm-topology.py)逐条核对固件原始字节，
回放初始化包的整数控制流及 28 字复制循环，并分别测试 FP load/store 的先更新与后更新解释。
738 组合成案例覆盖空、完整、单点、稀疏和不连续掩码及不同活动掩码；
两种 FP 解释不影响上述映射字段。锁、邮箱和外设使用合成夹具，没有执行固件或硬件。
Ghidra 伪代码遗漏硬件循环，不能单独作为该结论的依据。

## 读取和失败规则

1. 校验 CPU、PCI、非虚拟机身份、物理地址位宽、精确 PM 版本和长度。
2. 查询 SMU 版本；只接受 `00732E00h`，再依次查询 16 个 `A5h` 目标。
3. 只有完整查询的 `FEh` 回复表示不存在。超时、拒绝、取消、索引/邮箱读写错误均直接失败。
4. 存在数必须与精确表版本中的 CCD 存储宽度相同；随后请求一次传输并读取 PM 表。
5. 重查身份、表版本、长度、地址及 SMU 版本，再查询完整掩码，并在查询后重查身份与 SMU 版本。
6. 前后掩码一致才发布表和映射。失败保留诊断计数，清除 PM 缓冲和映射结果。

`A5h` 的存在路径会刷新时钟遥测并返回打包时钟数据；本功能只使用存在回复。
它不读取第二 rails，也不请求调参写入。服务事务不能排除固件或其它进程的并发访问，
前后相等不能证明采样原子性或发现中间发生又恢复的变化。

JSON 的 `data.native.ccd_mapping.firmware_ccd_ids_by_slot` 保存映射，
`valid/rechecked` 表示这些读取检查通过；`os_cpu_mapping_verified`、
`active_core_mask_verified` 和顶层 `physical_mapping_verified` 仍为 `false`。
导入文件时从原始 PM 字节重新解析数值，不把文件中可伪造的 live 映射声明作为硬件事实。

## 字段单位与第二 rails 的剩余工作

MP5 累加函数 `37B60h` 已定位到逐核结构 `11998h`、步长 `1C0h`。
下面是来源计算的进展，不是已经验证的 PM 输出单位：

| 行（从 0 开始） | 来源与导出行为 | 当前限制 |
|---|---|---|
| core 5/6/7 | `+70h/+78h/+7Ch`；`340B4h` 由计数器比值生成，`37D40h` 对对应累加槽乘 100 | 支持驻留比例/百分比候选；计数器物理含义和 FP 归一化语义仍需独立确认 |
| core 12/13 | `+10Ch/+108h`，计算中限制为 0..1 的比例 | 原版 `UOPs/MemBand` 标签不能当作单位证据 |
| core 2 | `+28h`，温度候选来自传感器有效位及 `raw/8 - 49` 计算 | 内部寄存器物理定义尚未闭合 |
| core 3/4 | `+68h/+F8h`，时钟及计数器推导候选 | 不把它们直接标为实测 GHz/MHz |

`37D72h` 的 FP 地址更新指令在通用 Ghidra 与 QEMU DFP 配置中有不同解释；
在该问题解决前继续保留原始存储值和未验证单位，不将乘 100 直接等同于可靠百分比。

双 rails 的 `61h` 保存路径、第二字段零值镜像、模式守卫和裁剪已由既有指令回放覆盖。
两组状态槽位地址为 `E248h` 和 `E250h`，状态索引不是 CCD 号。
第一字段已有消费者，第二字段的物理轨归属、消费者与回读命令尚未闭合。
`62h/63h/64h` 是 MP5 写入/广播路径，`67h` 是 VF 曲线查询路径；不能拿来充当 rails getter。
GUI/CLI 继续提供离线 rails 编码预览，运行时 `61h` 写入仍关闭。

此项静态研究、模拟后端测试和跨系统构建均不能替代真机验收。
